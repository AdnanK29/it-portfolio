CITM301 · Academic project

Investigating Windows Networking from Configuration to Support Handoff

Adnan Khan

I completed five Windows diagnostics labs in a university-provided Azure VM. I worked from host and adapter settings through DNS, DHCP, processes, network endpoints, routes and firewall state, then collected the output into a support record.

Tools and environment

Windows VM in Azure; Command Prompt; ipconfig, ping, nslookup, tasklist, netstat, netsh, tracert, pathping, arp, nbtstat; Notepad.

Individual coursework by Adnan Khan. May-June 2025. The VM was provided for the labs.

Establish the workstation and network baseline

I checked the host and Ethernet 2 adapter before interpreting any failed network test. The configuration records a Microsoft Hyper-V adapter, IPv4 10.0.0.176 with a /20 subnet, gateway 10.0.0.1, and DNS/DHCP server 168.63.129.16.

Separate name resolution from reachability

I pinged a public hostname and received timeouts after the name resolved. I then used nslookup to query DNS directly. The returned address supports a working lookup; the missing echo replies leave the remote ICMP path unconfirmed.

Read aliases and service-related DNS records

I extended the DNS checks to aliases, MX records and an SRV query. These queries ask different questions: the address behind a name, mail destinations, or service records. I read the returned record type rather than treating every answer as proof that an application was reachable.

Inspect processes and their hosted services

I used tasklist to inventory processes and tasklist /svc to see the services associated with them. This connects a process identifier to service ownership and provides context before investigating a listening port or a busy process.

Check DHCP renewal after losing remote access

The DHCP release exercise interrupted the remote session. I recorded that symptom, then checked ipconfig /renew. The renewed adapter output again shows 10.0.0.176 and gateway 10.0.0.1. This is a recovery configuration check, not a diagnosis of every connectivity issue.

Inspect, clear and revisit the DNS cache

I inspected cached records with ipconfig /displaydns, cleared the resolver cache with ipconfig /flushdns, and reviewed later records after browsing. The flush command returned a success message. Later cache entries show that DNS information was collected again.

  • I also practised tree for directory structure and console colour commands; those supporting exercises do not need repeated screenshots.

Connect network endpoints to processes

I used netstat -a to inspect listeners and connections, then netstat -o to include process IDs. I also inspected TCP connections, UDP endpoints and the dynamic TCP port range with netsh. These outputs describe endpoints and allocation settings at the time of the lab.

Check the local stack and compare IP versions

IPv4 loopback and IPv6 localhost each returned four replies with zero packet loss. I kept those local checks separate from traceroute tests: the IPv4 traces had limited replies, while the IPv6 trace could not resolve its target.

Review neighbors, routes and device identity

I inspected ARP and IPv4 neighbor information, then reviewed the route table and assigned DNS servers. I also used getmac, hostname and nbtstat for device identity. The default route identifies the gateway; a neighbor entry is a local mapping rather than a full remote path.

Inspect firewall state and preserve the investigation

I recorded the firewall state and port-exception views using the commands provided in the labs. Those legacy netsh firewall commands display deprecation warnings. I then appended hostname, route, interface and connection output to Q1.txt and opened it in Notepad for a support handoff.

  • The collection uses >> to append. The pathping command appears separately in the source, so I do not claim its output was saved to Q1.txt.

Put the troubleshooting findings together

The evidence shows valid addressing, successful DNS answers and working loopback tests alongside incomplete ping and trace results. I narrowed the problem without declaring a root cause that the tests did not establish. A next investigation would test the affected application port and review the applicable network policy.

What I learned

  • Use separate tests for DNS, the local stack and the remote path.
  • Connect endpoint information to process and service ownership.
  • Record commands and observed results so another technician can continue the investigation.
